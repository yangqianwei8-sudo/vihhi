## S0-3: 现状结论（只写事实）

### 3.1 已存在的后台能力

1. ✅ **WorkflowTemplate 模型** - 完整的流程模板定义
   - 字段: `code`, `name`, `status`, `applicable_models`, `form_filter_conditions` 等
   - Admin 已注册，UI 完整

2. ✅ **UniversalApprovalService 基类** - 统一的审批服务接口
   - 提供 `submit_approval()`, `approve()`, `reject()` 等方法
   - 模板选择逻辑: `get_workflow()` 按 `WORKFLOW_CODE` 查找

3. ✅ **业务服务层** - 各业务模块有独立的审批服务类
   - `LoanApprovalService`, `SealUsageApprovalService`, `SealBorrowingApprovalService`, `OpportunityApprovalService`, `PlanApprovalService`
   - 都通过写死的 `WORKFLOW_CODE` 常量选择模板

4. ✅ **Admin 管理界面** - WorkflowTemplate 可配置
   - 可编辑 `applicable_models`（多选下拉框）
   - 可配置 `form_filter_conditions`（JSON 字段）

### 3.2 缺口清单

1. ❌ **缺少独立的绑定配置表**
   - 无法实现: `content_type` + `action` → `workflow_template` 的显式绑定
   - 无法实现: 同一业务对象的不同操作（如 plan 的 start/cancel）通过配置区分

2. ❌ **缺少唯一生效规则**
   - 如果存在绑定配置，需要确保同一 `content_type` + `action` 只能有 1 条启用配置

3. ❌ **缺少配置优先机制**
   - 业务代码都是写死 `WORKFLOW_CODE`，没有"先读配置，找不到再兜底"的逻辑

4. ❌ **缺少审计字段**（如果新增绑定模型）
   - `updated_at` / `updated_by` 需要补充

5. ❌ **缺少防呆校验**
   - 保存绑定配置时，需要校验模板存在、action 合法、启用冲突提示

6. ❌ **缺少 Admin UI**
   - 没有专门的"流程绑定配置"管理页面

### 3.3 可复用 vs 需新增

**可复用扩展**:
- ✅ `WorkflowTemplate` 模型 - 无需修改，继续使用
- ✅ `UniversalApprovalService.get_workflow()` - 可扩展为"配置优先、兜底原逻辑"
- ✅ Admin 基础框架 - 可复用 `BaseModelAdmin`, `AuditAdminMixin`

**必须新增**:
- ❌ `WorkflowBinding` 模型 - 绑定配置表
- ❌ `WorkflowBindingAdmin` - 绑定配置管理页面
- ❌ 配置查询服务方法 - 在 `UniversalApprovalService` 中新增"配置优先"逻辑
- ❌ 业务服务层改造 - 让各业务服务支持"配置优先"
